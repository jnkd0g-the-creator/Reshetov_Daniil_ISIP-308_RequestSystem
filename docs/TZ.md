# Техническое задание: CoffeeDesk

Версия 1.0 · 12.11.2026 · Решетов Даниил, ИСИП-308.

## 1. Назначение и проблема предметной области

CoffeeDesk — система создания и учёта эксплуатационных заявок сети кофе-баров.
Типовые обращения: протекает кран у мойки, кофемашина не набирает давление,
перегорел светильник, повреждён стул, требуется хозяйственное обслуживание.
Пользователи — сотрудники баров, диспетчерская служба и технические специалисты.

Без единой системы сотрудники передают неисправности в мессенджере или устно.
Сообщения теряются среди текущих обсуждений, а фотографии и пояснения оказываются
в разных переписках. Смена заканчивается, но следующая смена не знает, обращался
ли кто-то за ремонтом. Один и тот же протекающий кран получает несколько устных
обращений, при этом ответственный не назначен. Управляющий вынужден отдельно
уточнять, кто выехал в бар, какие работы выполнены и можно ли снова пользоваться
оборудованием. Неисправность кофемашины непосредственно мешает продажам;
неисправности сантехники и электрики требуют повышенного внимания к безопасности.

Программа связывает обращение с конкретным кофе-баром, сохраняет описание,
категорию, приоритет и автора. Оператор видит общий список, назначает мастера и
контролирует движение заявки. Исполнитель работает с назначенными ему заявками
и фиксирует результат комментарием. Заявитель видит только свои обращения и
может уточнить проблему. История статусов не исчезает при архивации. Поиск и
фильтры помогают найти обращение без просмотра переписки. Результатом внедрения
должен стать проверяемый процесс «сообщили → назначили → выполнили → приняли»,
а не обещание автоматически устранить неисправность или гарантировать время
ремонта. Аварийные ситуации по-прежнему требуют звонка ответственному.

## 2. Роли и права

| Роль | Разрешённые действия | Ограничения |
|---|---|---|
| Заявитель (`applicant`) | Создать заявку, видеть свои, редактировать свою новую, комментировать свои | Не видит чужие; не назначает мастера и не меняет статус |
| Оператор (`operator`) | Видеть все, создать/редактировать, назначить мастера, последовательно менять статус, комментировать | Не архивирует, не управляет учётными записями |
| Исполнитель (`technician`) | Видеть назначенные ему, комментировать, переводить новую в работу и в работе в выполненную | Не назначает, не закрывает, не редактирует реквизиты |
| Администратор (`admin`) | Все действия оператора, архивировать закрытые, просмотр архива | Не обходит порядок статусов; интерфейс управления пользователями вне MVP |

Все действия требуют входа. Справочники доступны любой вошедшей роли.
`GET /users` отдаёт только публичные сведения (без хешей, паролей, сессий).
Заявителю доступна только собственная запись пользователя, остальным — список
для назначения. Пользователи создаются локальной административной командой/seed,
публичной самостоятельной регистрации нет.

## 3. Функциональные требования

- **FR-01.** Система должна аутентифицировать пользователя по логину и паролю, завершать сессию при выходе и проверять права на сервере.
- **FR-02.** Система должна создавать заявку с темой 3–120 символов, описанием 10–4000 символов, существующими баром/категорией и приоритетом `low/normal/high/urgent`.
- **FR-03.** Система должна автоматически присваивать номер `CB-00001`, автора из сессии, дату UTC и статус «Новая», не доверяя этим полям клиента.
- **FR-04.** Система должна показывать список только доступных пользователю заявок и карточку с реквизитами, комментариями и историей.
- **FR-05.** Система должна искать доступные заявки по номеру, теме и описанию без учёта регистра кириллицы, совместно с фильтрами.
- **FR-06.** Система должна фильтровать по статусу, категории и кофе-бару; поддерживать ограничение размера выдачи и смещение.
- **FR-07.** Система должна изменять тему, описание, категорию, бар и приоритет с проверкой прав; закрытые и архивные заявки недоступны для редактирования.
- **FR-08.** Система должна разрешать назначать только существующего активного пользователя роли «Исполнитель»; снять назначение можно только у новой заявки.
- **FR-09.** Система должна проводить только переходы «Новая → В работе → Выполнена → Закрыта». Переход в работу требует исполнителя. Повторное присвоение текущего статуса идемпотентно, без новой записи истории.
- **FR-10.** Система должна разрешать исполнителю менять статус только собственной назначенной заявки до «Выполнена»; закрывать может оператор или администратор.
- **FR-11.** Система должна сохранять комментарии длиной 1–2000 символов и историю изменений статуса/назначения/архивации вместе с автором и временем.
- **FR-12.** Система должна архивировать только закрытую заявку и только администратором, после явного подтверждения. Физическое удаление бизнес-заявок не предусмотрено.
- **FR-13.** Система должна сообщать об ошибках валидации, доступа, отсутствии объекта и недоступности БД понятным сообщением без трассировки и SQL.
- **FR-14.** Система должна предоставлять REST API над теми же сервисами, справочники пользователей, статусов, категорий, баров и OpenAPI.
- **FR-15.** Система должна предоставлять `/health` с проверкой доступности БД, повторяемую инициализацию и запуск в Docker с сохраняемым томом данных.
- **FR-16.** Система должна отображать русскоязычный интерфейс входа, списка, создания, карточки и редактирования; состояния загрузки, ошибок и пустого результата.

## 4. Нефункциональные требования

- **NFR-01, удобство.** Основные действия доступны с клавиатуры, поля подписаны, статус различается текстом, не только цветом; интерфейс работает при ширине 390 и 1440 px.
- **NFR-02, надёжность.** Создание/изменение заявки и её истории атомарны; FK включены для каждого соединения; после перезапуска данные не пропадают.
- **NFR-03, производительность.** На учебном стенде с 1000 заявок 95% из 30 последовательных запросов списка занимают <1 с. Это локальный ориентир, не SLA промышленной сети.
- **NFR-04, безопасность.** Пароли хранятся как PBKDF2-SHA256 с солью (600000 итераций); сессии случайны, в БД только хеш, срок 8 ч; HttpOnly/SameSite cookie, CSRF для изменения данных, Secure в production, параметризованный SQL.
- **NFR-05, сопровождаемость.** Четыре слоя, отсутствует SQL в контроллерах; ≥10 автотестов и документированный запуск одной командой.
- **NFR-06, воспроизводимость.** Python 3.10+, фиксированные прямые зависимости, schema/seed, инструкция из чистого окружения; локальные секреты и рабочая БД не публикуются.
- **NFR-07, конфиденциальность.** В репозитории, отчётах и видео только вымышленные данные; публичный учебный снимок БД не содержит рабочих паролей и сессий.

## 5. Сущности

Role — права; User — пользователь с ролью; Cafe — кофе-бар; Category — категория;
Status — состояние; Request — заявка с автором/исполнителем;
Comment — уточнение; RequestHistory — аудит; Session — ограниченная по времени сессия.
Связи 1:M: роль–пользователи, бар–заявки, категория–заявки, статус–заявки,
пользователь–созданные/назначенные заявки, заявка–комментарии/история.

Категории: сантехника, кофейное оборудование, электрика, мебель, хозяйственные работы.
Тестовые бары: «Центр», «Парк», «Вокзал». Все адреса и сотрудники учебные.

## 6. Пользовательские сценарии (Use Case)

| ID / актор | Предусловие и действия | Результат / альтернатива |
|---|---|---|
| UC-01 / любой | Ввести логин/пароль, нажать «Войти» | Список; неверные данные → общее сообщение без раскрытия существования логина |
| UC-02 / заявитель, оператор, администратор | Открыть форму, описать протечку, выбрать сантехнику и бар, отправить | Новая заявка с номером; пустое поле → ошибка, запись не создана |
| UC-03 / любая роль | Открыть список, ввести «кран», выбрать статус и категорию | Только доступные совпадения; нет совпадений → пустое состояние со сбросом фильтров |
| UC-04 / оператор, администратор | Открыть новую заявку, выбрать мастера, назначить, перевести в работу | Сохранён исполнитель, статус и история; не-мастер → 422 |
| UC-05 / исполнитель | Открыть назначенную, оставить комментарий о ремонте, отметить выполнение | Выполнена; чужая заявка недоступна |
| UC-06 / оператор, администратор | Убедиться в результате, закрыть выполненную | Закрыта; прямой скачок из новой запрещён |
| UC-07 / заявитель | Изменить описание собственной новой заявки | Данные сохранены; после начала работ редактировать может только оператор/администратор |
| UC-08 / администратор | Открыть закрытую, нажать архив, подтвердить номер заявки | Скрыта из общего списка, доступна в архиве; отмена ничего не меняет |

## 7. Критерии приёмки

| Критерий | Проверяемый результат |
|---|---|
| AC-01 | 4 роли входят; запрос без сессии → 401, запрещённое действие → 403 или скрытый объект 404 |
| AC-02 | Создание валидной заявки → 201, уникальный номер, поля и дата сохранены в SQLite |
| AC-03 | Пустая тема, 121 символ, неверная категория/приоритет → 422, новых строк нет |
| AC-04 | Поиск «КРАН» находит «кран», фильтры пересекаются, чужие заявки не раскрываются |
| AC-05 | Нельзя начать работу без мастера; все 3 последовательных перехода и история сохраняются |
| AC-06 | После PATCH и повторного чтения/перезапуска новые значения остаются |
| AC-07 | Архив требует admin, закрытый статус и подтверждение; данные/история не удаляются |
| AC-08 | Есть ≥10 заявок, ≥4 пользователей, ≥4 категории; 5 экранов и OpenAPI доступны |
| AC-09 | Docker запускается из инструкции; health проверяет БД; данные переживают пересоздание контейнера |
| AC-10 | ≥20 документированных кейсов, ≥10 автотестов, реальные логи; блокировки не выданы за успех |

## 8. Границы проекта и уточнения после анализа ИИ

Не входят: платежи, закупки, вложения, email/SMS, реальный SLA, мультиорганизационная
изоляция, публичная регистрация, управление паролями через UI. Отказ от этих
функций удерживает учебный проект в проверяемом объёме.

Проверены три неоднозначности чернового анализа: «удалить» заменено на архивировать
закрытые; «любая роль меняет статус» ограничено таблицей ролей; «быстрый поиск»
заменён измеримым ориентиром NFR-03. Проверка: сопоставление UC-04/05/08,
матрицы прав и AC-04/05/07. Приёмка студентом отдельно, агент не подменяет её.
