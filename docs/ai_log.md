# Единый AI-журнал CoffeeDesk

Модель всех записей: **GPT-6.1 Sol**, идентификатор `openai/gpt-6.1-sol`.
Платформа: OpenCode, текущая рабочая сессия, 12.11.2026.

## Происхождение записей

Исходный пользовательский запрос (полностью):

> Выполни задания из папки tasks, следуй чётко инструкциям из файла. Создавай отчёт о выполнии лабораторных в DOCX. Чётко следуй заданиям. После каждого заметного этапа пуш изменения в git, прогу будем делать для кофе-баров. Создание и учет заявок для кофе баров. Аля заявка на починку крана, и тд.

Уточнение пользователя (полностью):

> python используй 3.10 из локального .venv, его я создал специально под этот проект, пароль с ssh-доступа убрал, теперь он должен быть доступен, docker так же установил.

Далее сохранены **внутренние проектные подзапросы и ответы того же ИИ-агента**,
сформулированные при выполнении этих указаний. Это не экспорт отдельных
сообщений пользователя, не независимая экспертиза и не обращения к другим
моделям. Решения и инструментальные проверки агента явно отделены от
самостоятельного вклада студента. Студент ещё должен просмотреть артефакты,
повторить ручные проверки и подтвердить приёмку. Ниже нет утверждений, будто
студент уже самостоятельно выполнил команды или записал видео.

Для каждого этапа фиксируются: задача, полные формулировки, контекст, результат,
обоснование модели/формулировки, принято/изменено, способ фактической проверки,
а также то, что осталось студенту. Скриншоты и логи — только результаты проекта.

## ЛР 1 — анализ требований

**Задача/контекст:** исходная просьба пользователя, методичка ЛР1, кофе-бары.

**Запрос 1 (свободный):**
> Предложи требования к системе учёта заявок кофе-баров: например, на починку крана. Кто ею пользуется и что она должна уметь?

**Ответ на запрос 1:** сотрудники создают обращения, диспетчер назначает мастера,
мастер выполняет, управляющий контролирует; нужны создание, список, поиск,
статусы, комментарии и удаление; интерфейс должен быть удобным и быстрым.
Сущности: пользователь, заявка, категория, статус, комментарий.

**Запрос 2 (структурированный):**
> Выступи аналитиком учебного проекта CoffeeDesk на Python 3.10/FastAPI/SQLite. Предметная область — эксплуатационные заявки кофе-баров, включая ремонт кранов и кофемашин. Определи четыре роли: администратор, оператор, исполнитель, заявитель. Дай матрицу прав, минимум 10 требований в форме «Система должна», минимум 5 измеримых нефункциональных требований, минимум 5 сущностей, минимум 5 сценариев и критерии приёмки. Используй ровно статусы Новая, В работе, Выполнена, Закрыта. Уточни, кто назначает мастера, кто закрывает заявку, что означает удаление и какие данные видит заявитель. Не добавляй платежи, SMS и публичную регистрацию. Выдели двусмысленности исходного варианта.

**Ответ на запрос 2 / использовано:** матрица 4 ролей, 16 ФТ, 7 НФТ,
9 сущностей, 8 UC, 10 AC в `docs/TZ.md`. Состояния последовательные;
заявитель видит свои; удаление — подтверждённый архив закрытых.

**Сравнение/почему промпт:** свободный вариант не определял доступ, удаление
и критерий скорости. Структурированный задаёт проверяемые ограничения и формат.
**Почему модель:** доступная модель текущей сессии умеет сопоставлять длинную
методичку, требования, Python и тесты; сравнения с другими моделями не проводилось.
**Доработка агента:** уточнены архив, права смены статуса и локальный p95 вместо
непроверяемого «быстро». **Проверка:** таблицы UC/AC сопоставлены с правами;
инструментальные проверки появятся в ЛР6–10. **Вклад студента:** задаёт предметную
область и Python; самостоятельная проверка итогового ТЗ ещё требуется.
**Вывод:** контекст, роли и критерии уменьшают неоднозначность; ответ ИИ не приёмка.

## ЛР 2 — Git

**Задача/контекст:** существующий Git-репозиторий, исходные пользовательские файлы,
main, SSH origin; нужны ≥5 этапов, develop, merge и конфликт.

**Запрос 1:**
> Объясни безопасный Git-workflow для учебного проекта CoffeeDesk. Репозиторий уже инициализирован, есть origin и пользовательские изменения .gitignore и tasks. Предложи последовательность проверки, пяти осмысленных коммитов, создания develop, отдельного изменения, merge и push. Объясни риски merge, reset и force push. Не перезаписывай чужие файлы и не меняй Git-личность.

**Ответ:** проверить status/log/remote, явно добавлять файлы этапа; коммиты
структуры, ТЗ, диаграммы, отчёта, workflow; develop → main через no-ff; без reset
и force. Повторный init не нужен, существующую личность сохранить.

**Запрос 2:**
> Предложи .gitignore для Python 3.10, SQLite, pytest и Docker и объясни типичный конфликт одной строки README в main и develop. Покажи диагностику и разрешение с сохранением смысла обеих сторон. Дай пять содержательных сообщений commit. Учебный SQLite-снимок docs/database/coffee_demo.sqlite3 должен остаться в Git, рабочие базы и секреты — нет.

**Ответ/принято:** исключить venv, env, кэш, coverage, локальные БД; явное
исключение для обезличенного учебного снимка; конфликт проверить status/diff,
объединить строку, add/commit. **Изменено:** вместо создания конфликта в рабочем
проекте используется изолированный учебный репозиторий; init только в нём.
**Проверка:** `scripts/git_evidence.py`, реальные merge/push и история;
`docs/evidence/git_conflict.txt`, снимки истории/веток. Ошибка SSH была реальной,
после настройки пользователем push прошёл. **Почему модель/промпт:** контекст
существующей истории предотвращает ненужную переинициализацию и опасные советы.
**Вклад студента:** подготовка репозитория и исправление SSH пользователем;
команды этапа выполняет агент, повторить самостоятельно ещё нужно.
**Итог:** опубликованные осмысленные этапы, безопасная работа с ветками.

## ЛР 3 — архитектура

**Задача/контекст:** docs/TZ.md, четыре роли, SQLite, веб-формы и REST API.
**Запрос 1:**
> Для CoffeeDesk сравни минимум два архитектурных варианта: слоистый монолит и микросервисы. Требования: четыре роли, создание и редактирование заявок кофе-баров, назначение мастера, четыре последовательных статуса, поиск, комментарии, аудит, Python 3.10/FastAPI/SQLite. Сравни простоту, тестируемость, расширяемость, стоимость внедрения и соответствие учебному проекту. Опиши четыре слоя с запретами, пять ключевых компонентов с входом и результатом, структуру каталогов. Не предлагай распределённую инфраструктуру без обоснования.

**Ответ/принято:** модульный монолит, presentation → service → repository →
SQLite; качественное сравнение и пять контрактов в architecture/README.md.
**Запрос 2:**
> Проведи критическое ревью проектной схемы CoffeeDesk: UI и API вызывают RequestService/AuthService, сервис использует Repository, Repository работает с SQLite. Запись заявки и истории должна быть атомарной. Ищи SQL в контроллерах, ролевые решения в repository, обход прав прямым HTTP, глобальные соединения и избыточную связанность. Для каждого замечания предложи проверяемое исправление, не заявляй, что ещё не написанный код уже проверен.

**Ответ/решения:** права в сервисе, scope в сервисе, единый unit of work,
connection на сценарий — принято; микросервисы — отклонено. **Проверка:**
сопоставление diagrams/contracts/TZ, фактический запуск после ЛР6. **Почему
модель/промпт:** явные ограничения позволяют отличить проектный риск от
доказанного дефекта. **Доработка:** транзакция охватывает аудит, а не только
таблицу Requests. **Вклад студента:** самостоятельная проверка архитектуры
не заявляется выполненной. **Итог:** диаграммы и границы ответственности.
